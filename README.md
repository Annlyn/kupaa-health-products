# Kupaa Health Products

A full-stack e-commerce store: React storefront, admin console, Express API,
Prisma, Razorpay payments and Shiprocket shipping.

```
client/   React 18 + Vite + Tailwind + React Router
server/   Express + Prisma (SQLite by default, Postgres-ready)
```

## Quick start

```bash
npm install
npm run setup      # generates .env with fresh secrets, creates the DB, seeds demo data
npm run dev        # API on :4000, storefront on :5173
```

The admin console is at **/admin**.

### Signing in

Credentials are never printed in the UI, and no password ships in the production
bundle.

| Role | Email | Password |
| ---- | ----- | -------- |
| Admin | `admin@kupaahealth.com` | Generated by `npm run seed` and printed once, unless you set `ADMIN_PASSWORD` |
| Customer | `customer@example.com` | `Customer@123` — demo data, delete before going live |

Leave `ADMIN_PASSWORD` blank in `server/.env` and the seed generates a strong one
and prints it a single time; it is stored only as a bcrypt hash. To choose or
reset it, put a value in `server/.env` and run `npm run seed` — that rewrites the
admin password and revokes every existing session, so it doubles as account
recovery. The server refuses to start in production if `ADMIN_PASSWORD` is a
well-known default.

### Seeding is safe to re-run

`npm run seed` writes the demo catalogue **once**. After that it leaves products,
categories and coupons completely alone: it will never delete a product you added
or bring back one you deleted. It only ensures the admin account exists and
restores any missing placeholder images.

To wipe the demo catalogue and start over:

```bash
npm run seed:reset
```

That removes only products the seed itself created (archiving any that appear in
an order). Products you added are never touched.

## What is built

**Storefront** — catalogue with search, filters and pagination; product pages
with a variant selector, PIN-code delivery check and verified-buyer reviews;
cart and wishlist for guests and signed-in users; coupon codes; checkout with
Razorpay or COD; order tracking.

**Admin** — dashboard with revenue and stock; products (create, edit, duplicate,
archive, delete, bulk discount/activate/delete, per-option variants, image
upload); categories; orders with Shiprocket fulfilment, labels and refunds;
customers; coupons; reviews; and **Store settings**, where every piece of
storefront copy and every commerce rule is editable.

### Variants

A product is either a single SKU or offers options the customer picks from —
500 g / 1 kg / 2 kg. Each option carries its own price, MRP, stock, SKU and
shipping weight.

For a product with options, `Product.price`, `mrp` and `stock` become maintained
aggregates (the cheapest active option's price, and total stock). That keeps
every catalogue filter, sort and dashboard query working for both kinds of
product — see `server/src/services/variant.service.js`.

Cart rows and order items key on product **and** variant, so the same product in
two sizes stays two lines. Order items snapshot the variant name, so a later
rename never rewrites an old invoice.

## Deleting products

A product that appears in an order is **archived** by default, which hides it
from the store but keeps it linked from those orders. You can also **delete it
permanently**: `OrderItem` stores its own name, SKU, price and image, and the
foreign key is `SetNull`, so past invoices still read correctly — they just stop
linking to a product page. Both choices are offered in the admin.

## Deploying

### GitHub Pages cannot host this on its own

Pages serves **static files only**. It cannot run Node, Prisma, a database, file
uploads, or keep your Razorpay secret — so the API cannot live there. Anything
claiming otherwise would mean shipping your payment keys to the browser, where
every visitor can read them.

The working shape is a split:

| Part | Where | Why |
| ---- | ----- | --- |
| Storefront + admin UI | GitHub Pages | A static bundle — exactly what Pages is for |
| API, database, uploads, secrets | Render / Railway / Fly.io / a VPS | Needs a running Node process |

**Simpler alternative:** put everything on one Node host. `npm run build`, then
`npm start` — in production the API serves the built SPA itself, so there is one
origin, no CORS, and first-party cookies. Prefer this unless you specifically
want Pages.

### 1. Deploy the API

`render.yaml` in the repo root is a ready blueprint with Postgres included.

1. Change `provider` in `server/prisma/schema.prisma` from `sqlite` to
   `postgresql`. Prisma needs it as a literal, and SQLite would not survive a
   redeploy on an ephemeral disk.
2. Push to GitHub, then on Render pick **New → Blueprint** and select the repo.
3. Set `CLIENT_URL` to your Pages URL (`https://yourname.github.io`) and
   `SERVER_URL` to the Render URL.
4. Leave `ADMIN_PASSWORD` blank — the seed generates one and prints it once in
   the deploy log. Copy it immediately.
5. Run `npm run seed` once from the Render shell.

Any Node host works; it needs `DATABASE_URL`, the two JWT secrets, `CLIENT_URL`
and `SERVER_URL`.

### 2. Deploy the storefront to Pages

1. **Settings → Pages → Source: GitHub Actions**
2. **Settings → Secrets and variables → Actions → Variables → New variable**
   `API_URL` = your API base URL, e.g. `https://kupaa-api.onrender.com`
3. Push to `main`. `.github/workflows/deploy-pages.yml` builds and publishes, and
   fails with a clear message if `API_URL` is unset rather than shipping a
   storefront that cannot reach an API.

The build handles the three things that otherwise break on Pages:

- `VITE_BASE` sets the `/<repo>/` sub-path, and the router picks it up via
  `import.meta.env.BASE_URL`;
- `404.html` is emitted as an SPA fallback, so deep links like
  `/shop/product/honey` resolve instead of 404ing;
- `VITE_API_URL` points API calls **and product image URLs** at the API origin —
  images are stored as `/uploads/...` and would otherwise be looked up on Pages.

### Production checklist

1. Set `NODE_ENV=production` and real `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET`;
   the server refuses to start with placeholder secrets.
2. Set `CLIENT_URL` and `SERVER_URL` to your real origins — CORS and cookies
   depend on them. `CLIENT_URL` accepts a comma-separated list.
3. Use Postgres. SQLite writes do not suit more than one instance.
4. Give `server/uploads` a persistent volume, or move it to object storage.
5. Point webhooks at the API host: `/api/payments/webhook` (Razorpay) and
   `/api/shipping/webhook` (Shiprocket).

### Known limits of the split

- **Third-party cookies.** The refresh token is an httpOnly cookie. Across
  origins (`github.io` → your API host) Safari and Firefox block it by default,
  so a session ends when the 15-minute access token expires. Signing in still
  works; it just will not survive a reload. A custom domain with the API on a
  subdomain (`shop.example.com` + `api.example.com`) fixes this; single-origin
  hosting avoids it entirely.
- **Uploaded images** are written to the API's local disk, which most free tiers
  wipe on redeploy. The write path is isolated in
  `server/src/middleware/upload.js` if you move it to S3 or Cloudflare R2.

## Integrations

Both run in a safe mode until you add credentials:

- **Razorpay** — without keys the store offers cash on delivery only. Orders stay
  `PENDING` until the payment signature is verified server-side, so a spoofed
  success callback can never confirm an order.
- **Shiprocket** — without credentials it runs in **mock mode**, returning
  realistic serviceability, AWB and tracking data so the whole fulfilment flow is
  testable locally.

Admin → Integrations shows connection status, the environment variables each
needs, and the webhook URLs to paste into their dashboards.
