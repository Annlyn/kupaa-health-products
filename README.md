# Kupaa Health Products

A complete e-commerce store for a health & wellness brand: React storefront, Express + Prisma API,
JWT authentication, a full admin console, **Razorpay** payments and **Shiprocket** shipping.

Products are fixed catalogue items — no per-order customisation. A product is either a single SKU,
or it offers **variants** the customer picks from at checkout (500 g / 1 kg / 2 kg). The admin
defines which options exist; each carries its own price, MRP, stock, SKU and shipping weight.

```
kupaa-health-products/
├── server/          Express API, Prisma schema, Razorpay + Shiprocket integrations
└── client/          React 18 + Vite + Tailwind storefront and admin console
```

---

## Quick start

```bash
npm run setup     # installs both workspaces, creates the database, seeds demo data
npm run dev       # API on :4000, storefront on :5173
```

Then open **http://localhost:5173**.

The admin console lives at **/admin**.

`npm run setup` creates `server/.env` from `server/.env.example` with freshly generated JWT
secrets. An existing `.env` is never overwritten.

### Signing in

Credentials are never printed in the UI, and no password ships in the production bundle.

| Role     | Email                   | Password                                              |
| -------- | ----------------------- | ----------------------------------------------------- |
| Admin    | `admin@kupaahealth.com` | Generated by `npm run seed` and printed once, unless you set `ADMIN_PASSWORD` |
| Customer | `customer@example.com`  | `Customer@123` — demo data only, delete before going live |

Leave `ADMIN_PASSWORD` blank in `server/.env` and the seed generates a strong password and prints
it a single time; it is stored only as a bcrypt hash. To choose or reset it:

```bash
# put a new value in server/.env, then
npm run seed
```

Re-seeding with `ADMIN_PASSWORD` set rewrites the admin password **and revokes every existing
session**, so it doubles as the account-recovery path. With it blank, an existing admin's password
is left untouched.

The server refuses to start in production if `ADMIN_PASSWORD` is one of the well-known defaults, and
warns about it in development.

Out of the box the store runs **without** Razorpay or Shiprocket credentials: online payment is
hidden (cash on delivery only) and shipping runs in a mock mode that returns realistic couriers,
AWBs and tracking scans, so you can exercise the entire order lifecycle before signing up for
anything.

## What is built

### Storefront

- **Home** — hero, trust strip, category grid, bestsellers, new arrivals
- **Shop** — search, category / price / stock / bestseller filters, five sort orders, pagination
- **Product detail** — gallery, variant selector (price, stock, SKU, weight and courier estimate all
  follow the chosen option), stock urgency, PIN-code delivery check, spec sheet, verified-buyer
  reviews with a rating histogram, related products
- **Cart** — server-priced line items, coupon entry, free-shipping progress bar, slide-over drawer
- **Checkout** — saved or new address, live courier ETA for the PIN code, Razorpay or COD
- **Account** — profile, password change, order history with retry-payment and cancel, order
  detail with a live courier timeline, address book
- **Wishlist**, **public AWB tracking**, **policies**, and a 404 page

Guests get a working cart backed by `localStorage`. It is priced by the server on every change and
merged into the account cart on sign-in.

**Requests are made only when something actually needs them.** A first-time visitor's landing page
costs exactly one API call (`/api/store`, for the header and footer copy):

- the home page's category, bestseller and new-arrival sections fetch when they scroll into view,
  via `useFetchOnVisible`;
- a guest with an empty cart is priced locally — no `/cart/quote` round trip;
- the refresh-token call is skipped entirely for browsers that have never signed in;
- identical concurrent GETs share one request, and slow-moving paths (`/store`, `/categories`,
  `/products/facets`, `/payments/config`) are cached briefly and invalidated on any write;
- store settings are mirrored in `sessionStorage`, so the chrome paints instantly on later loads
  while revalidating in the background;
- every route below the top level is a lazy chunk, so admin code never ships to shoppers.

`useFetch(path, deps, { enabled })` gates a request behind a condition, so a component can mount
without touching the network and start fetching later.

### Admin console

- **Dashboard** — revenue (month / lifetime), 14-day revenue chart, order status breakdown, top
  sellers, low-stock alerts, recent orders, integration health
- **Products** — define the options a product is sold in (name, SKU, price, MRP, stock, weight, and
  an availability toggle per option); searchable table with URL-backed filters (linkable and
  back-button friendly),
  inline stock editing, duplicate-as-draft, and per-row edit/delete. Tick rows for bulk actions:
  apply or clear a percentage discount, activate, archive, feature, unfeature, delete. The product
  form has a discount control (type a percentage or use a preset and the selling price is
  recalculated from the MRP), image upload or URL, inventory, shipping dimensions and visibility
  flags
- **Categories**, **Coupons** (percent / flat, minimum order, cap, usage limit, validity window)
- **Orders** — filter by status, payment state, date range and free text; CSV export; per-order
  fulfilment: compare courier rates → create Shiprocket order → assign AWB → schedule pickup →
  pull label / manifest / invoice → track → refund
- **Customers** — lifetime value, order history, role and account-status control
- **Reviews** — moderation queue across every product; deleting one recalculates that product's rating
- **Store settings** — every piece of storefront copy and every commerce rule (see below)
- **Integrations** — connection status, required environment variables, webhook URLs to paste

### Store settings

Nothing customer-facing is hardcoded. Under **Admin → Store settings** you can edit, in six sections:

| Section | What it controls |
| ------- | ---------------- |
| Store identity | Name, tagline, support email and phone, currency |
| Pricing & delivery rules | Free-delivery threshold, flat shipping fee, tax percent, COD on/off, COD fee, max quantity per item |
| Announcement bar | The strip above the header, with an on/off switch |
| Home page | Hero badge, headline, paragraph, both buttons, stat tiles, highlight cards, trust strip, every section heading, and the closing promo panel |
| Footer & contact | Blurb, promise strip, fine print (contact details come from Store identity) |
| Policy pages | Shipping, returns, privacy, terms and contact copy — one paragraph per line |

Values live in the `Setting` table and are cached in memory. `.env` supplies the defaults, so an
untouched install behaves exactly as shipped; **Reset section** drops your overrides and falls back
to them. The form is generated from a server-side schema (`server/src/services/settings.service.js`),
so adding a setting there makes it editable with no UI change.

Commerce rules are not cosmetic — `freeShippingAbove`, `flatShippingFee`, `taxPercent`, `codExtraFee`
and `maxQtyPerItem` are read by the pricing service and the cart on every request, so changing one
immediately changes what customers are charged and what they may order.

## Payments — Razorpay

1. Get keys from **Razorpay Dashboard → Settings → API Keys** (`rzp_test_…` works for development).
2. Put them in `server/.env`:

   ```
   RAZORPAY_KEY_ID=rzp_test_xxxxxxxx
   RAZORPAY_KEY_SECRET=xxxxxxxxxxxxxxxx
   RAZORPAY_WEBHOOK_SECRET=pick-a-strong-string
   ```

3. Add a webhook at **Settings → Webhooks** pointing to `https://your-domain/api/payments/webhook`
   with the same secret, subscribed to `payment.captured`, `payment.failed` and `refund.processed`.

**How the flow is secured.** `POST /api/orders` reserves stock and creates a `PENDING` order, then
asks Razorpay for a payment order. The browser opens Razorpay Checkout. On success the client posts
the signature to `POST /api/payments/verify`, which recomputes the HMAC over `order_id|payment_id`
server-side — a forged callback cannot confirm an order. The webhook is the safety net: if the
customer closes the tab after paying, `payment.captured` confirms the order anyway, and
`payment.failed` releases the reserved stock. Both paths funnel through one `confirmOrder()`, which
is idempotent, so a race between them cannot double-count a coupon or create two shipments.

Prices are never taken from the client. `services/pricing.service.js` recomputes the subtotal,
coupon discount, shipping and tax from the database on every quote and at checkout.

## Shipping — Shiprocket

1. Create an API user at **Shiprocket → Settings → API → Configure** (this is *not* your dashboard
   login).
2. Fill in `server/.env`:

   ```
   SHIPROCKET_EMAIL=api-user@yourdomain.com
   SHIPROCKET_PASSWORD=...
   SHIPROCKET_PICKUP_LOCATION=Primary      # the nickname of your pickup address
   SHIPROCKET_PICKUP_PINCODE=600001        # origin for rate and ETA checks
   SHIPROCKET_WEBHOOK_TOKEN=pick-a-strong-string
   ```

3. Add a webhook pointing to `https://your-domain/api/shipping/webhook`, sending the token in the
   `x-api-key` header. Courier scans then move orders to `SHIPPED` / `DELIVERED` / `RETURNED`
   automatically.

What the integration covers: bearer-token auth with in-memory caching and refresh-on-401,
serviceability and courier rate cards, adhoc order creation, AWB assignment, pickup requests,
label / manifest / invoice generation, AWB tracking and shipment cancellation.

**Mock mode.** With no credentials, `services/shiprocket.service.js` returns deterministic fake
couriers, AWBs and tracking scans instead of calling the API. Every screen and workflow behaves
normally; the admin console labels the shipment as simulated.

Product weight and dimensions are required for real Shiprocket rates — they are on the product form
and default to a 300 g parcel.

## Data model

SQLite by default so there is nothing to install. To move to Postgres, change `provider` in
`server/prisma/schema.prisma` to `postgresql`, point `DATABASE_URL` at your database and run
`npm run db:push -w server`. No model changes are needed.

Seventeen models: `User`, `RefreshToken`, `Address`, `Category`, `Product`, `ProductImage`,
`ProductVariant`, `CartItem`, `WishlistItem`, `Coupon`, `Order`, `OrderItem`, `OrderEvent`,
`Shipment`, `Review`, `Setting`, `WebhookLog`.

### Variants

A product with no `ProductVariant` rows behaves exactly as before. Add options and the customer must
choose one before adding to the cart; `Product.price`, `Product.mrp` and `Product.stock` become
**maintained aggregates** — the cheapest active option's price and the total stock across options.
That is what lets every catalogue filter, sort and dashboard query stay unchanged for both kinds of
product (`services/variant.service.js#syncProductAggregates`).

Cart rows and order items key on product **and** variant, so the same product in two sizes stays two
lines. Order items snapshot `variantName`, so a later rename never rewrites an old invoice, and the
Shiprocket label reads "Whey Protein Isolate (1 kg)". Deleting an option that appears in an order
deactivates it instead.

Two more deliberate choices worth knowing:

- **Order items and shipping addresses are snapshots.** Renaming a product or editing an address
  never rewrites history, so old invoices stay correct.
- **Products that appear in orders are archived, not deleted.** `DELETE /api/admin/products/:id`
  detects this and flips `isActive` instead.

## Authentication

- 15-minute JWT access token, sent as `Authorization: Bearer …`, kept in memory with a
  `localStorage` mirror so a page refresh does not sign you out.
- Opaque refresh token stored in the database and delivered as an `httpOnly`, `SameSite` cookie
  scoped to `/api/auth`. It rotates on every use and is revoked on logout, password change and
  account deactivation.
- Passwords are bcrypt hashes (cost 12). Login compares against a dummy hash when the email does not
  exist so response timing does not leak which addresses are registered.
- `express-rate-limit` guards the API generally (300/min) and credential endpoints specifically
  (20 per 15 min, successful attempts excluded).

The API client refreshes transparently on a 401 and replays the request; concurrent 401s share a
single refresh.

## Order lifecycle

```
PENDING ──► CONFIRMED ──► PACKED ──► SHIPPED ──► DELIVERED
   │            │            │           └────► RETURNED
   └────────────┴────────────┴───────► CANCELLED
```

Transitions are validated server-side in `services/order.service.js`; the admin UI only offers legal
next steps. Cancelling restores reserved stock inside a transaction. Every change writes an
`OrderEvent`, and both the customer and the admin see the same timeline.

## Deployment notes

1. Set `NODE_ENV=production` and real values for `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` — the
   server refuses to start in production with placeholder secrets.
2. Set `CLIENT_URL` and `SERVER_URL` to your real origins (CORS and cookies depend on them).
3. `npm run build`, then `npm start`. In production the API serves `client/dist` from the same
   origin, so cookies need no cross-site configuration.
4. Uploaded images are written to `server/uploads`. On an ephemeral filesystem, mount a volume there
   or switch `middleware/upload.js` to S3 / Cloudinary.
5. Move to Postgres before running more than one API instance — the Shiprocket token cache is
   per-process, which is fine, but SQLite writes are not.

  buttons, then asserts the database changed: create a product, edit it, inline stock edit, delete
  it, create a coupon (and confirm it discounts a real cart), create a category, apply a discount
  preset on the product form, bulk discount / archive / delete a selection, and duplicate a product.
  21 flows, all passing.
- **Variants** — price range on cards, selector on the product page, per-option stock rules, a
  guest cart holding the same product in two sizes as two lines, checkout decrementing the exact
  variant, cancellation restocking it, per-variant shipping weight reaching Shiprocket, and the
  admin adding then removing an option through the real form. 24 UI checks and 27 API checks.
- **API** — register / login / refresh, cart and coupon pricing, PIN-code serviceability, COD
  checkout, review posting, admin stats, courier rate comparison, shipment creation with AWB and
  pickup, document generation, tracking, status transitions (including a rejected illegal one),
  product and coupon CRUD, and CSV export.
- **Settings** — a commerce-rule change altering real checkout totals (shipping ₹99, 18% tax), a
  content edit surfacing on `/api/store`, the per-item cap enforced on both add and update,
  validation rejecting an out-of-range tax and an empty store name, review deletion recalculating a
  product rating, and reset restoring the `.env` defaults.
- **Storefront** — every route mounted in jsdom against the live API as guest, customer and admin,
  failing on any console error; each settings section rendered; and an admin edit verified to appear
  on the home page, then reverted by reset.
